# C5 — Reflection

**Habib Shouman**

I drew the boundaries around effects rather than the number of internal helper calls. The Data tool returns one catalogue entry without writing anything. The Action tool persists one local session at a supplied location and does not choose a space. The Orchestration tool supplies the catalogue lookup result to that same write operation. It is a fixed workflow within a tool, whereas the surrounding model-driven agent chooses an operation from the user's request and interprets feedback. Keeping shared application methods outside the MCP decorators makes these boundaries testable without requiring a model, while stdio integration tests separately exercise the protocol boundary.

Three tools fit this narrowly scoped demonstration, although the coordinator is a convenience rather than an essential source of intelligence: an agent could call the two primitives itself. Central coordination makes lookup-before-write behavior inspectable and avoids relying on the model to reconstruct that sequence correctly. The main engineering tradeoff is that a simple local record is easier to test than a live booking service, but cannot establish real room availability or reserve a room. Useful next steps are an authoritative catalogue connector, user-level access controls, and a separate scheduling capability if the scope expands. Before claiming reliable natural-language routing, I would run a documented set of unseen requests with a fixed provider/model, record tool choices and effects, and report failures separately from deterministic software checks.
